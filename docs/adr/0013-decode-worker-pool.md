# 0013 - The sandboxed decode worker: crates, protocol, levels, switches

- **Status:** accepted (implementation; CI evidence in [testing/sandbox-worker.md](../testing/sandbox-worker.md))
- **Date:** 2026-10-15
- **Roadmap items:** S.15, M6.05, M6.06 (AppContainer), M6.10 (fault injection), M6.41, M6.42, M6.43, M8.30-M8.33, M9.50-M9.56 (the boxes are the owner's to tick; the evidence is in the testing page)
- **Decision log links:** D3, B12, A-9; builds on [0006](0006-decode-sandbox.md) (the spike) and [0009](0009-heif-decode-backend.md) (the libheif backend)

## Context

ADR-0009 left HEIC and AVIF parsed inside the application's own process, "acceptable for the owner's own use, not for a public release". ADR-0006 showed per OS how far a helper can be confined. This ADR records how the helper is built.

## Decision

1. **Three pieces, OS code kept out of the core.**
   - `auto-crop-codecs` gets a small seam, `remote::RemoteDecoder` (a trait object installed once per process). After the parent-side checks (file size, safe-Rust header walk, pixel cap, memory estimate, unsupported features) a decode of a format the remote decoder handles goes there, and the reply is re-checked against the same `DecodeLimits` (`remote::check_reply`: size, orientation, frames, profile length). Without an installed decoder nothing changes. `decode_in_process` is the explicit in-process entry the worker itself uses.
   - `auto-crop-sandbox` (new): the framed protocol, the pool client, per-OS launch and confinement, and `worker_rt` (everything the worker does apart from decoding). All `unsafe` is in `src/os/ffi/` (SAFETY-commented, `cargo xtask ci-guards`); `docs/policy/ci-guards.md` lists it.
   - `auto-crop-worker` (new, binary `auto-crop-worker`): a thin `main` over `worker_rt` with `heif` (libheif, dav1d, libde265) behind a cargo feature. No `unsafe`, no network crate. It is the only place the C libraries run once the pool is installed (the parent keeps them linked for the header-less in-process fallback and `doctor`).
2. **Start-up order is the security argument.** Resource limits, then *preload* (set the libheif plugin folder, `heif::init` which `dlopen`s the plugins, one warm-up decode of an embedded 48x32 AVIF so dav1d's threads and lazy parts exist), then *confine*, then `Hello`, and only then the first `Job` frame: the input bytes arrive after the sandbox is in place. A worker that cannot apply its sandbox exits without reading anything. After confining, the worker **probes itself** (open a user-private location, connect to a TCP port, start a process: each must fail) and puts the observation in `Hello`; `doctor` prints it. A level is therefore never a claim of the parent.
3. **Control channel: stdin and stdout pipes, length-prefixed and versioned** (`proto.rs`): `ACWP`, version, kind, 64-bit length, payload. Hand-written fixed-layout messages (little-endian integers, length-prefixed strings), every length checked against a per-kind cap before anything is allocated; `Result` payloads are capped by the job's metadata cap. No general serialisation format and **no pixels** on the pipe. The worker's own stdout is moved aside (Unix `dup2`, Windows `SetStdHandle`) so a library that prints cannot corrupt a frame. The reader never panics on hostile bytes (tests: truncations at every byte, wrong magic and version, a length of 2^63).
4. **Pixels through shared memory; input through the pipe.** Linux: an anonymous `memfd` inherited as fd 3, resized (`ftruncate`) by the pool for each job and truncated to zero afterwards; macOS: the same with an unlinked temp file (`mkstemp`-style, `0600`); Windows: a pagefile-backed file mapping **per job**, duplicated into the worker with `DuplicateHandle` (read and write access only), its handle value sent in the job header. The pool copies the pixels out once, with a fallible allocation. The worker writes at most `w * h * 3` bytes into a mapping sized by the pool from the header probe; a reply claiming more is a protocol error.
5. **Levels, per OS, reported by the worker** (tiers `full` > `reduced` > `process-only` > `none`):
   | OS | `full` | fallbacks (each reported) |
   |---|---|---|
   | Windows | AppContainer with no capabilities + job object (1 active process, per-process commit limit, kill-on-close, UI restrictions, die-on-exception) | restricted token + job (`reduced`: files blocked, the network is not), then job only (`process-only`) |
   | Linux | `RLIMIT_AS/CPU/CORE` + Landlock ABI 4 (all file and TCP access handled, none granted) + seccomp allow-list + `PR_SET_DUMPABLE=0` | seccomp without Landlock (`reduced`, level text `landlock=unavailable(...)`), then limits only |
   | macOS | `sandbox_init` with `(deny default)` plus `sysctl-read`, `RLIMIT_CORE=0` | none (the worker refuses to run unconfined and exits; the pool reports it) |
   The pool refuses a worker below `PoolConfig::min_tier`. On Windows the process is created suspended, assigned to the job, then resumed: no unconfined instant. The AppContainer profile `autocrop.decode.worker` is created on first use and left in place (a few registry entries per user; `os::delete_profile` removes it for tests and an uninstaller).
6. **Windows staging.** An AppContainer cannot read a folder it was unzipped into. The first start copies the worker, the DLLs beside it and the libheif plugin folder into `%LOCALAPPDATA%\AutoCrop\worker-stage\<fingerprint>` (fingerprint of names, sizes and times; stale fingerprints removed) and grants read-and-execute to ALL APPLICATION PACKAGES, ALL RESTRICTED APP PACKAGES and RESTRICTED with `icacls`. Only DLLs and the plugin folder are copied; a development build finds its DLLs through `PATH` and `LIBHEIF_PLUGIN_PATH`, which staging follows.
7. **Seccomp.** The allow-list (`os/linux.rs`) is memory management, futexes, signals for panics, clocks, `getrandom`, `read`/`write`/`close` on open descriptors, `pread`/`pwrite`, `fcntl`, `dup`, `sched_getaffinity`, thread start (`clone` only with `CLONE_THREAD`; `clone3` answers `ENOSYS` so glibc uses `clone`), `prctl` for thread names only, `ioctl` for two terminal queries. Everything else, `openat`, `socket`, `execve`, `ptrace`, `mount` included, answers `EPERM`. The filter is applied to every thread (`TSYNC`) and is never switched off; it was widened by test (the `strace` audit in `worker.yml` fails on any denied call besides the escape probes), not by guessing. `EPERM` rather than kill so a denial is observable in the escape tests; both stop the call.
8. **The pool** (`pool.rs`): workers start on demand up to `min(cores / 2, 4)` and are reused; each worker is sized (address space or commit limit) for `max(job pixel cap, 100 MP)` as 16 bytes per pixel plus 1 GiB, and a job with a higher cap gets a fresh, larger worker; a worker is retired after 64 jobs. A job has a wall-clock budget (`max_decode_ms`, else 10 s + 1 s per declared megapixel) enforced by killing the worker, and the worker is told 90% of it so libheif cancels itself first. A dead, crashed, timed-out, cancelled or protocol-violating worker is replaced and the job gets a typed error (`WorkerCrashed`, `MemoryLimit`, `DecodeTimeout`, `Cancelled`); a Rust allocation failure in the worker prints `memory allocation of N bytes failed`, which the pool reads as `MemoryLimit`. Back-pressure: at most `inflight_cap` bytes (input plus pixel memory; the engine passes its `MemoryBudget` cap) are admitted at once, FIFO-ish, with one oversize job admitted alone; the engine's own `MemoryBudget` permit still wraps every decode. Cancellation: `with_cancel(token, ...)` (the engine wraps the skeleton stages and the convert decode) kills the worker within about 20 ms. Parent threads wait on the reply with a poll, never block on a stuck pipe (the job is written by a scoped thread).
9. **Switch.** `AUTOCROP_DECODE=inproc|worker|auto`, default `auto`: HEIC and AVIF go to the worker when `auto-crop-worker` sits beside the executable and can start; otherwise they decode in this process with a one-time stderr notice and the level `none` in `doctor`. JPEG, PNG, TIFF, WebP and BMP stay in-process (safe-Rust decoders) unless `worker` is forced; `worker` never falls back (a forced decode without a worker is an error). A JPEG decode that libjpeg-turbo would do (`turbojpeg` feature, scaled) is routed to the worker too when `worker` is forced.
10. **Test hooks never ship.** The escape attempts, the fault injection (abort, exit, hang, 3 GiB allocation, garbage on the channel, panic) and "pretend Landlock is absent" exist only with `--features escape-tests` on `auto-crop-worker`/`auto-crop-sandbox`. `crates/worker/tests/guard.rs` fails when a worker built without the feature contains one of their strings or when any other manifest names the feature; the package scripts and smoke tests repeat the check on the shipped binary.

## Consequences and open items

- **Not done here:** `SetDefaultDllDirectories` and dropping `PATH` for the worker on Windows (M6.08; the worker gets `System32` only when confined, but the parent process itself is not hardened), `--require-sandbox`/the "refuse HEIC unsandboxed" setting (M6.54, M6.57; the pool has `min_tier`, nothing exposes it), kill-mode seccomp for release (`EPERM` today), per-arch syscall derivation on aarch64 (the list is shared and checked on the ARM runner), cgroup v2 limits, Windows 10 and the Surface (UNMEASURED), macOS 12 and a real Mac (UNMEASURED), the macOS memory watchdog tuned on a real workload.
- `birdcage` stays banned (GPL-3.0). New dependencies: `landlock` (MIT OR Apache-2.0), `seccompiler` (Apache-2.0 OR BSD-3-Clause), both Linux-only.
- A level of `process-only` or `none` is still crash and memory isolation; it is not confinement. The README of each package says which level the CI runners reached and that no real hardware was used.
