# Codecs: limits, probe, decode guard and the hostile-file gate

Roadmap: M1.12 (sniff and probe), M1.13 (`DecodeLimits`), M1.14 (decode guard), M1.15 (JPEG, PNG), M1.16 (TIFF, WebP), M1.17 (EXIF orientation, ICC), M1.20 (lossless JPEG transform, safe-Rust variant), M1.69 (hostile-file corpus). Design: [PLAN 3.1, 3.6, 3.10](../plan/03-image-io-formats.md). Code: `crates/codecs` (all safe Rust, `forbid(unsafe_code)`) and `xtask/src/hostile.rs`.

## How to run

```
cargo test -p auto-crop-codecs        # 79 tests (+1 ignored timing test): 39-fixture probe table, limits, decode, orientation,
                                      # mutation sweep, lossless JPEG transforms
cargo xtask make-hostile              # 89 hostile files, each decoded in its own process
cargo xtask make-hostile --only png   # a subset (substring of the case name)
```

`cargo test -p xtask` runs the same corpus (`xtask/tests/hostile.rs`), so the gate runs on every OS lane that runs `cargo nextest run --workspace`. All fixtures are generated by code (`crates/codecs/src/fixtures.rs`, `hostile.rs`, behind the `fixtures` feature); nothing binary is committed. The tests that need an external oracle call `magick` (ImageMagick with libjpeg-turbo 3.2.0, libtiff 4.7.2, libwebp 1.6.0) and skip with a message when it is not installed.

## Pipeline order (PLAN 3.10.1)

`sniff` (magic bytes) -> file-size cap -> container parser (`probe_with`: size, depth, frames, scans, orientation, ICC size; metadata, scan and frame caps) -> pixel cap (`TooLarge`) -> `est_bytes` cap -> plausibility checks -> `image` decoder with `image::Limits` -> the decoder's own dimensions are checked again -> orientation applied once.

`probe` allocates nothing proportional to the file or the image (measured below). `DecodeLimits` fields, each with its own test (`suite/limits.rs`): `max_pixels` (100 MP, clamped to the 500 MP ceiling), `max_file_bytes` (256 MiB, JPEG and WebP), `max_file_bytes_streamed` (2 GiB, PNG and TIFF), `max_metadata_bytes` (16 MiB per EXIF, XMP or ICC blob), `max_scans` (100), `max_frames` (10,000), `max_est_bytes` (`pixels x 9 + 64 MiB`), `max_decode_ms` (soft timeout).

## Decode accuracy (measured)

- zune-jpeg 0.5.15 versus libjpeg-turbo 3.2.0 (through ImageMagick), 96x64: 4:4:4 mean abs diff 0.013 LSB (max 2); 4:2:0 0.271 (max 3); 4:2:2 0.164 (max 2); progressive 4:2:0 0.271 (max 3). Bound in the test: 1.5 LSB (PROVISIONAL, from M1.15). CMYK and YCCK conversions are identical to libjpeg-turbo + ImageMagick (0.000).
- image-webp versus libwebp 1.6.0 on a lossy VP8 file: bit-identical (`inf` dB PSNR). Lossless WebP, PNG (8 and 16-bit, palette, Adam7) and uncompressed, LZW, Deflate and PackBits TIFF are bit-exact (16-bit sources within 1 level after the reduction to 8-bit).
- A 1-bit Group 4 TIFF written by libtiff 4.7.2 and one written by the `fax` encoder both decode, without inversion, for WhiteIsZero and BlackIsZero.

## Lossless JPEG transform (M1.20): `codecs::jpeg_lossless::transform`

Safe Rust, no libjpeg-turbo: the file is entropy-decoded to DCT coefficients, blocks are moved (flips negate odd rows or columns of a block, transposes swap (u, v) and the quantisation table), and the result is written back as a baseline JPEG with Huffman tables optimised for the new data (T.81 Annex K.2). Every other segment (JFIF, EXIF, XMP, ICC, Adobe, comments) is copied byte for byte, so the Orientation tag is untouched. Ops: `Rotate90/180/270`, `FlipH`, `FlipV`, `Transpose`, `Transverse`, `Crop(Rect)`; `Policy::Perfect` refuses what cannot be exact, `Policy::Snap` trims partial edge MCUs (mirroring ops) or grows a crop to the MCU grid, and the result reports the realised `rect` and a `perfect` flag. Supported input: 8-bit sequential Huffman JPEG, any sampling factors, restart intervals, one interleaved scan; progressive, arithmetic, lossless, 12-bit and one-scan-per-component files are `UnsupportedFeature` (the caller re-encodes them).

| Check | Result |
|---|---|
| Decode of the output versus rotating the decoded source, 6 variants (grey, 4:4:4, 4:2:0, 4:2:2, 4:4:0, 4:2:0 with restart) x 7 ops | mean abs diff at most 0.04 LSB (grey, 4:4:4) and 0.03 (subsampled); max 2 and 3. Rotate180 and both flips are exact (0). The ADR-0004 bound "within 2 levels" holds for grey and 4:4:4; 4:2:x reach 3 at the edge (upsampling filter) |
| The inverse op, and four quarter turns | pixel-exact: the coefficients are restored |
| libjpeg-turbo 3.2.0 decoding every output | agrees with zune-jpeg within 1.5 LSB for all 42 outputs (our Huffman tables and entropy coding are valid for an independent decoder) |
| A libjpeg-turbo-made 4:2:0 file, Rotate90 versus ImageMagick's pixel rotation | mean 0.30 LSB, max 3 |
| Partial MCUs (70 x 50, 4:2:0, 16 x 16 MCU) | `Perfect` refuses every mirroring op; `Snap` trims only the mirrored axes (70 -> 64, 50 -> 48) and reports `perfect: false`; Transpose is perfect at any size |
| Crop | origin snaps down and far edge up to the 16-pixel grid (request 20,10 30x30 gives 16,0 48x48), an aligned or image-edge crop is `perfect`, empty and outside rectangles are errors |
| 1,000 reused transforms of one input | identical output every time |
| Byte-mutation sweep of the transformer, and the JPEGs of the hostile corpus (budgets as for decode) | 0 panics |
| 12 MP (4000x3000, 4:2:0, 383 KB smooth file) | Rotate90 215 ms, FlipH 164 ms, a 2000x1500 crop 64 ms (dev profile, one thread; a photographic file has far more entropy data and will be slower: M1.56 should measure it) |

The roadmap's "1000 reused buffers ASan-clean" is an FFI concern (caller-owned `TJPARAM_NOREALLOC` buffers); this implementation has no unsafe code and no reused foreign buffers, so the reuse test checks determinism instead, and M1.18 and M1.19 still own the turbojpeg variant. Not covered by a test: progressive input (refused), non-interleaved baseline input (refused), restart-interval *preservation* (the output has no restart markers).

## Findings and decisions that differ from, or add to, the plan

1. **`png` expands `iCCP` without a bound** (found by the corpus). The container parser now inflates the chunk itself under `max_metadata_bytes` before the PNG decoder sees it. The same cap covers EXIF and XMP; JPEG APP segments cannot exceed it.
2. **zune-jpeg decodes a JPEG whose data is far shorter than its header claims as a success with grey fill**, and `image` runs it in non-strict mode. Policy (not in the plan): a JPEG without an end-of-image marker is `Corrupt`, and so is a JPEG smaller than one bit per 8x8 luma block of its declared size. Rationale: B3 overwrites originals, so a silently grey-filled result is data loss. Cost: a JPEG truncated by a few bytes, which some viewers show, is refused; the owner can relax this with a "salvage" option later.
3. **Plausibility checks before allocation** (not in PLAN 3.10.1): PNG smaller than unpacked size / 1100 (deflate cannot beat about 1032:1), uncompressed TIFF smaller than its pixel data, and the JPEG rule above. They stop a 140-byte file from making the decoder reserve 95-381 MiB at the 100 MP cap.
4. **`core::DecodeLimits` and `codecs::DecodeLimits` differ.** Core's (M1.08) is `Copy` with five fields and one 2 GiB `max_file_bytes`; PLAN 3.10.1 says 256 MiB for worker formats and 2 GiB for streamed TIFF and PNG, and the codecs need `max_est_bytes` and `max_decode_ms`. The codecs type is a superset used by `decode_with`. To reconcile when the core `Decoder` port is implemented for the codecs: map core's `max_file_bytes` to `max_file_bytes_streamed` and keep the 256 MiB default for the others. Not done here: that port is engine wiring.
5. **16-bit and bilevel sources become RGB8.** `Decoded.raster` is still the 8-bit `imgproc::Raster`; 16-bit TIFF and PNG are reduced with the notice `depth.reduced_to_8` and `source_bit_depth` records the original. Keeping 16 bits needs the `core::Raster` (M1.08) in the engine.
6. **Notices** (PLAN 3.1 rule 7), as stable codes in `Decoded.notices`: `tiff.multi_page`, `anim.first_frame_only` (animated WebP, APNG), `alpha.dropped` (only when some pixel is not opaque), `depth.reduced_to_8`, `cmyk.naive_conversion`, `icc.invalid` (a JPEG ICC with a gap or duplicate sequence number is dropped, never repaired).
7. **JPEG 12-bit, arithmetic-coded, lossless and DNL files are `UnsupportedFeature`**, decided from the frame header before any decoding (PLAN 3.11 allows this). The 12-bit fixture is an 8-bit file with its precision patched: no encoder or tool available here writes a genuine 12-bit JPEG (ImageMagick's build writes 8-bit when asked for 12).
8. **image-webp composites animated frames through an alpha blend**, so the first frame can differ from the stored pixels by one level (observed 255 -> 254). Static WebP is exact.
9. **Soft timeout.** `decode_guarded(Arc<[u8]>, &DecodeLimits)` with `max_decode_ms` returns `DecodeTimeout` at once and leaves the worker thread running; everything the closure owns (the input bytes, and a `MemoryBudget` hold once M2.03 wires it) is released only when the thread ends. A panic inside the thread is still caught. `pool_panic_handler` is the handler every rayon pool must install (`ThreadPoolBuilder::panic_handler`); without it rayon aborts the process on an un-joined task panic. M2.03 must install it on the engine pools.
10. **The engine still lists only `jpg`, `jpeg`, `png` as candidates** (`engine::enumerate::is_candidate`) and maps `UnsupportedFeature`, `DecodeTimeout` and `InternalPanic` onto the codes the UI has copy for (`UnsupportedFormat`, `Internal`). Both are one-line follow-ups once the UI has the strings.
11. **`xtask` contains the only `unsafe` of this work**: the counting `GlobalAlloc` in `xtask/src/alloc_count.rs` (peak heap per hostile file, portable on three OSes). It is a developer tool, never shipped. The M1.72 `ci-guards` allow-list for `unsafe` must include it or move it.
12. **Dependencies added** (all permissive, `cargo deny check` green): `image` features `tiff` and `webp` (pulls `tiff` 0.11.3, `image-webp` 0.2.4, `fax`, `weezl`), `zune-jpeg` pinned `=0.5.15`, `flate2` (already in the tree through `png`) for the bounded iCCP inflate; behind the `fixtures` feature, `jpeg-encoder` 0.7.1 (`(MIT OR Apache-2.0) AND IJG`), `tiff` and `fax` as encoders.
13. **Subsampled JPEGs with one scan per component are `UnsupportedFeature`** (found by the M1.70 fuzzers, see [fuzzing.md](fuzzing.md)): zune-jpeg 0.5.15 panics in its AVX2 IDCT on them. The marker walk refuses them before decoding; 4:4:4 files with one scan per component still decode.
